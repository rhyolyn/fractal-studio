Codex Architectural Analysis

An independent, source-code-only architectural review. Existing design documents were intentionally excluded so that findings reflect the code as-built rather than the code as-intended.

Date2026-05-30
ReviewerCodex
Scopeui/ + core/ source only

Executive summary

RESOLVED Six of the seven findings from this review have been resolved. The boundaries are now real: settings have a single aggregate write path, services are Qt-free, the composition root is a single construction pass, and the backend is a consistent null object. The one remaining architectural risk is synchronous rendering on the UI thread (F2).

This document is an independent, source-code-only review conducted on 2026-05-30. The findings drove a four-plan architecture cleanup (arch-01 through arch-04) completed on 2026-05-31. Status annotations have been added to each finding below.

Original assessment: The codebase was partway through a refactor. Key dependencies still flowed through concrete Qt widgets, private MainWindow state, and synchronous backend calls. The highest-risk issues were settings persistence overwriting sibling fields, rendering/export work blocking the UI thread, and the section ports layer depending on a half-wired MainWindow.

Review method

Based on source files under ui/ and core/ only. Generated docs were not used as inputs.

Python cd ui && python -m pytest -q 11 passed, 143 deselected (at review time — now 23 passed)
Rust cd core && cargo test -q 24 passed (fixed by F7 resolution — fixture moved into repo)

Key findings

F1Settings writes can erase each otherHIGHRESOLVED

Theme persistence writes a fresh UiSettings(theme=name), losing any existing sidebar_collapsed values. Sidebar collapse persistence reads from MainWindow._current_ui_settings, which is not updated when the theme changes.

User-visible behavior: changing the theme can erase sidebar state; toggling a sidebar section after a theme change can save the old theme back to disk.

Fix  Centralize settings updates behind one aggregate update path. Each write should load the current full UiSettings, replace exactly one field, and save the whole object: def update_settings(repo, transform: Callable[[UiSettings], UiSettings]) -> UiSettings
F2Rendering and export block the UI threadHIGHDEFERRED

Viewport rendering calls the Rust backend synchronously from the Qt event path. Export calls QApplication.processEvents() as a workaround. There is no Python-side worker abstraction, no cancellation, no progress reporting, and no render generation token.

Fix  Introduce a render job boundary. Components: RenderRequest (formula, bounds, dimensions, palette), RenderResult (request id, bytes, status), RenderWorker (off-thread Rust calls), RenderScheduler (coalesces viewport requests, drops stale results), ExportJob (long-running workflow with progress and cancellation). The existing debounce timer dispatches work rather than rendering directly.
F3Section ports depend on a half-built MainWindowHIGHRESOLVED

The factory builds section ports from window before context is attached. The base adapter reaches into owner._sections_state, a private object populated later. The composition root is split across main_window_factory.py, MainWindow.attach_context(), and MainWindowSectionsState.bind().

Fix  Construct repositories, services, controllers, coordinators, backend, and panel states directly in main_window_factory.py. Build section port adapters from explicit panel state objects, not from MainWindow. Keep MainWindow responsible for shell lifecycle only.
F4Application and service layers import concrete Qt widgetsMED-HIGHRESOLVED

The application/service layer accepts or imports QWidget, QFileDialog, QApplication, FractalViewportWidget, FractalParamsPanel, ColorCubeEditor, and PalettePreviewWidget. Export service reads viewport state and palette directly from FractalViewportWidget; palette service owns file dialog calls; favorites controller restores directly into widget instances.

Fix  Push widget reads/writes to the UI edge and pass data transfer objects inward. Better signatures: ExportService.export_render(request: RenderRequest, destination: Path, status: Callable), PaletteWorkflowService.save_palette(path, control_points, palette_size).
F5Backend availability is a partial facade, not a null objectMEDRESOLVED

CoreBackend.profile() returns defaults when Rust is absent, but operational methods call _require() and raise. Other callers check backend.available manually. The contract is inconsistent: is it a null object with safe defaults, or a required dependency that must be guarded before use?

Fix  Split capability description from execution. Introduce BackendCapabilities(can_render, can_generate_palette, ...) and explicit backend protocols (RenderBackend, PaletteBackend). UI enables/disables features from capabilities; execution code depends on protocol types.
F6MainWindowSectionsState is state holder and composition sub-rootMEDRESOLVED

Stores repositories, services, controllers, coordinators, backend state, section state, and widget references. Its bind() method constructs six panel state machines and wires lambdas between them — at least three distinct jobs for one class. Dependencies become available through broad shared state rather than explicit constructor arguments.

Fix  Reduce to a panel-state container. Construction belongs in the composition root: @dataclass class MainWindowSectionsState: viewport / sidebar / palette / colormap / favorites / export
F7Rust test suite has a path assumptionMEDRESOLVED

cargo test -q fails in tests::legacy_palette_parser_reads_existing_repo_map because a referenced path is not found from core/. The Rust core cannot be verified with one standard command.

Fix  Move the fixture into core/tests/fixtures/, or compute the path relative to CARGO_MANIFEST_DIR and skip if the external sample is intentionally optional.

Architectural strengths

  • Clear Python UI / Rust core split with a compact PyO3 bridge that is easy to locate.
  • state.py uses frozen dataclasses for persisted state — immutable and serializable.
  • The UI has begun moving widget behavior into controllers and coordinators.
  • Pytest markers configured so the default Python test run stays lightweight without PySide6.
  • Meaningful Rust unit coverage for palette generation, rendering variants, and serialization.
  • SectionPanel / ViewportWell direction is good: focused widgets with narrow responsibilities.

Bottom line

At review time: The app was not badly architected; it was mid-refactor. The main risk was that architectural names were cleaner than the actual dependency flow. The recommended next steps were: one settings aggregate owner, one composition root, application services that operate on data rather than widgets, and a consistent backend contract.

Current status: All four of those steps are done. The one remaining item from this review — async rendering (F2) — is a separate planned effort. The codebase is no longer mid-refactor.
