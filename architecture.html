Architectural Design

Fractal Studio is a layered PySide6 desktop app wrapped around a Rust renderer through a lazy-loading bridge. This page maps the structure, the design choices, and the debt that still deserves a raised eyebrow.

Date2026-05-28
ScopePython UI layer + Rust bridge
VersionPost-refactor

Executive summary

A Boundaries are real and rendering is async. All major structural debts are resolved and rendering no longer blocks the UI thread — viewport renders and PNG exports run on a background QThread via RenderWorker and ExportRunner.

Fractal Studio is a PySide6/Qt desktop application for interactive fractal rendering and palette editing. It wraps a Rust rendering engine (fractal_core) with a lazy-loading Python bridge and presents a seven-panel workspace: fractal viewport, palette editor, colormap editor, parameter controls, export controls, favorites gallery, and sidebar.

Three rounds of layering work have cleaned the architecture substantially. The first round split MainWindowController, reorganised adapters, introduced the discriminated union for formula parameters, and added constructor injection for panel states. The second round made all four key boundaries real: a single aggregate settings write path, Qt-free services and application controllers, a single-pass composition root, and a consistent CoreBackend null-object contract with an explicit BackendCapabilities type. The third round moved rendering off the UI thread: RenderWorker + RenderScheduler handle viewport renders via a 50 ms debounce and generation-counter stale-drop; ExportRunner handles PNG exports without blocking the event loop.

Layered architecture

The architecture follows a strict unidirectional dependency rule enforced by test_import_policy.py: lower layers do not know about higher layers.

Data model

All domain objects in state.py are frozen dataclasses: immutable, hashable, and serializable. The important structural choice is the discriminated union for formula-specific parameters, which makes invalid combinations unrepresentable at the type level.

Diagram 2
Domain Object Class Hierarchy
ViewportState ◆── {StandardParams · JuliaParams · PhoenixParams · NewtonParams} · FavoriteSnapshot ◆── ViewportState

from_dict() handles both the current structured format, with a formula_params.type discriminator key, and the legacy flat format. Callers do not have to know migration happened, which is exactly how migration code should behave when it is behaving itself.

Dependency injection & factory

main_window_factory.py is the composition root. A single create_main_window() function builds everything in one pass — repositories, services, controllers, coordinators, backend, then panel states with explicit collaborators — before attaching the result to the window. There is no deferred wiring phase.

Diagram 3
Factory / Composition Root
create_main_window() → repos + services + controllers + coordinators + backend → MainWindow shell → on_status → panel states → MainWindowSectionsState → build_sections_ports() → sections → window.initialize_sections()

Mediator / ports pattern

The ui/sections/ layer uses a Ports & Adapters pattern. sections.py builds the Qt layout by calling Protocol methods, without knowing the business logic, widgets, or adapter implementations.

SOLID principles

SSingle Responsibility

✓ Applied well

  • Export / Favorites / Theme / Settings controllers each own exactly one domain.
  • state.py is pure data — representation and serialization only.
  • sections.py has one job: build a Qt layout from port objects.

△ Still imperfect

  • MainWindowFavoritesState has many constructor parameters across separate concerns.
  • Services are Qt-free but some application coordinators still have Qt coupling.
OOpen / Closed

✓ Applied well

  • Port Protocols allow new adapters without touching sections.py.
  • FormulaParams union is extensible: add a dataclass + update from_dict().

△ Still imperfect

  • A new UI panel requires changes in 5 places (protocol, adapter, state, mediator, layout).
  • A new formula requires extending the backend interface.
LLiskov Substitution

✓ Applied well

  • Any class satisfying a port can substitute for another — real adapter or test double.
  • CoreBackend wraps None with a null-object facade returning safe values.

✓ Applied well

  • CoreBackend is now a pure null object — _require() deleted, all methods return safe defaults. BackendCapabilities makes the contract explicit.
IInterface Segregation

✓ Applied well

  • Seven distinct port interfaces instead of one monolithic set.
  • BackendPanelPorts has a single method — nothing forced on implementers.

△ Mildly imperfect

  • ColormapPanelPorts has 9 methods — wider than the others; worth watching.
DDependency Inversion

✓ Applied well

  • Controllers receive repositories and services via constructor injection.
  • main_window_factory.py is the explicit composition root.
  • Panel states depend on collaborator protocols, not concrete Qt widgets.

✓ Applied well

  • Panel states no longer accept MainWindow — status access injected as on_status: Callable[[str], None].
  • bind() deleted — factory owns all construction; wiring is explicit and inspectable.

Deficiencies

D1MainWindowSectionsState was a partial god object ✓ FIXED

MainWindowSectionsState is now a plain @dataclass with 6 typed panel-state fields. bind() is deleted. Panel-state construction moved entirely to main_window_factory.py.

D2validate() used string attribute names ✓ FIXED

validate() now iterates dataclasses.fields(self) — complete coverage by construction, no hardcoded list.

D3No test markers ✓ FIXED

unit and integration markers configured in pyproject.toml. Default pytest run executes unit tests only, green without PySide6. A startup smoke test catches full-factory wiring regressions.

D4Panel states accepted MainWindow directly ✓ FIXED

owner: MainWindow removed from all panel state constructors. Status messages go through an injected on_status: Callable[[str], None] extracted from the window's status bar at construction time.

D5Backend null-object inconsistently applied ✓ FIXED

CoreBackend is now a pure null object — _require() deleted, all operational methods return safe defaults when Rust is absent. BackendCapabilities frozen dataclass exposes explicit capability flags; UI reads capabilities, application/services layers make no availability checks.

D6Render timer has no teardown guard ✓ FIXED

The async rendering work resolved this. The viewport's QTimer now only calls RenderScheduler.schedule() (instant, non-blocking). The worker thread is stopped via render_thread.quit(); render_thread.wait(2000) on app exit. Stale in-flight renders are dropped by the generation counter.

D7ThemeWorkflowCoordinator persist side effect ✓ FIXED

apply_theme_name() has an explicit persist: bool parameter. Settings writes now go through SettingsRepository.update(), which performs an atomic read-modify-write, eliminating the stale-cache bug where theme changes erased sidebar collapse state.
